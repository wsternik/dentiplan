# Quotes Data Foundation (F-01) Implementation Plan

## Overview

Establish DentiPlan's data layer: a single `quotes` table in Supabase that stores each quote's full working tree (teeth, per-tooth pricelist items, visits, general items) as a Zod-validated JSONB `content` blob, plus the immutable approval snapshot, the cryptographic patient token, the dentystka's reference e-mail, and the lifecycle timestamps that later slices need. The schema is protected by deny-by-default RLS, exposes the public patient page through a single `SECURITY DEFINER` RPC, and guarantees approved-quote immutability with a database trigger. A synchronized TypeScript + Zod type layer turns the JSONB contract into a real type the rest of the app can depend on.

This is the load-bearing foundation for S-01 (end-to-end quote flow), S-02 (LLM prefill), S-03 (admin list), and S-04 (retention). It contains no UI, no API endpoints, no business logic, and no token *generation* — only the schema and the security objects that enforce its invariants.

## Current State Analysis

- **No domain schema exists.** `supabase/` contains only `config.toml` (Postgres 17, local API on 54321, db on 54322). There is no `supabase/migrations/` directory; this change creates the project's first migration.
- **No `src/types.ts`.** CLAUDE.md mandates shared entities/DTOs live there; it must be created. The `supabase` CLI (v2.23.4) is a devDependency, so `supabase gen types` is available.
- **Auth is single-operator and already wired.** Supabase SSR cookie sessions live in `src/lib/supabase.ts:5` (`createClient(headers, cookies)`); `src/middleware.ts:11` resolves `context.locals.user`; `App.Locals.user` is typed in `src/env.d.ts:3`. There are no roles — one dentystka is the sole authenticated operator.
- **The patient page is unauthenticated.** `/p/<token>` (built in S-01) must read a quote with no dentystka session, by secret token only.
- **`@supabase/ssr` uses the anon key** (`SUPABASE_KEY` in `astro.config.mjs:18`). There is no service-role key in the runtime, and this plan deliberately does not introduce one.

### Key Discoveries:

- The pricelist is **not** a DB table — F-02 defines it as a repo-seed JSON. In the database, pricelist values appear only inside the approved-quote snapshot. (roadmap.md F-02, lines 77–89)
- The roadmap pre-settled two load-bearing calls: the snapshot is held **inline as jsonb** in the quote row, and the token is generated by `crypto.getRandomValues` (≥128 bit) at approval time in S-01 — **not** by a DB sequence. (roadmap.md F-01 Risk, line 74; S-01 Risk, line 105)
- FR-053 requires an approved quote to be permanently read-only ("forensic snapshot"); FR-050 requires later pricelist edits to never change approved quotes. A whole-content freeze on approval satisfies both.
- FR-060 requires a generic "Link nieaktywny lub nieprawidłowy" for any invalid/unknown/non-approved token with **no information disclosure** — the read path must not reveal whether a token ever existed.
- FR-066 / FR-072: the patient page must never expose `patient_email` or any identifier; the e-mail is admin-only and never sent to the LLM.

## Desired End State

After this plan, against a local Supabase instance (`supabase db reset`):

- A `quotes` table exists with: `id uuid` PK, `patient_type`, `status` (`draft` | `approved`), a unique-indexed raw `token`, nullable `patient_email`, a `content jsonb` (live working tree, frozen on approval), `created_at`, and `approved_at`.
- RLS is **on** and deny-by-default. The authenticated dentystka can do all CRUD on her own rows; the `anon` role has **no** direct table access.
- `select get_quote_by_token('<approved-token>')` returns a single patient-safe row (no email, no draft data); the same call for an unknown or draft token returns **zero rows** — indistinguishable cases.
- An `UPDATE` to a row whose stored `status` is already `approved` raises an exception; the `draft → approved` transition itself is allowed.
- `npm run build` / `astro check` pass with `src/db/database.types.ts` regenerated and `src/types.ts` exporting the domain types + Zod schemas.
- A checked-in SQL probe (`supabase/tests/quotes_foundation_probe.sql`) asserts every guarantee above and passes.

## What We're NOT Doing

- **No token generation.** The `token` column exists; `crypto.getRandomValues` generation happens in S-01 at approval.
- **No pricelist table.** Pricelist is a repo seed (F-02). Only the snapshot inside `content` holds pricelist values.
- **No cost calculation.** Anesthesia-fee rules (FR-042/043), totals, and ranges are computed in S-01; the `content` shape merely has room to *store* resolved values.
- **No UI, no API endpoints, no services.** No `/admin/*`, no `/p/<token>` page, no `src/pages/api/quotes/*`. Those are S-01/S-03.
- **No retention/expiry logic.** S-04 owns the 12-month enforcement; F-01 only provides `created_at` / `patient_email` columns it will act on.
- **No token hashing at rest.** Raw indexed token (decided); revisit only as S-05 hardening if ever wanted.
- **No second/service-role secret** in the Cloudflare Worker.

## Implementation Approach

A single `quotes` table is the entire relational footprint. Each quote's structured working data lives in one `content` jsonb column whose shape is owned by a hand-written Zod schema (`QuoteContentSchema`), validated at every app boundary in later slices. Because `content` is already one atomic document, freezing a quote on approval is just "stop allowing the row to change" — enforced by a `BEFORE UPDATE` trigger — and the snapshot is simply the content as it stood at approval (no separate blob).

Security is layered in the database, not the app: RLS denies the `anon` role everything; the single public read path is a `SECURITY DEFINER` function that returns only patient-safe columns for `approved` tokens and nothing otherwise. This keeps the public route on the anon key (no service-role secret), encodes FR-060's no-disclosure rule in one place, and makes the guarantees testable by SQL before any UI exists.

Types flow schema → code: `supabase gen types` produces row types that stay mechanically in sync with migrations, while the jsonb `content` (which the generator sees only as `Json`) gets a real hand-written type plus Zod validator in `src/types.ts`.

## Critical Implementation Details

- **`SECURITY DEFINER` hardening.** The RPC must be owned by a role that can read `quotes`, have a pinned `search_path` (e.g. `set search_path = ''` with fully-qualified `public.quotes`) to avoid search-path injection, and be granted `EXECUTE` to `anon` while `anon` has no table privileges. Returning a typed row (or `setof`) of whitelisted columns — never `select *` — is what keeps `patient_email` and draft rows off the public path.
- **Immutability trigger scope.** The trigger must read `OLD.status`: block when `OLD.status = 'approved'`, allow when `OLD.status = 'draft'` (including the draft→approved transition that sets `approved_at`). A naive "block all updates on approved rows including the approving update" would make approval itself impossible. The trigger guards **UPDATE only** — DELETE of approved rows is deliberately left to the row owner, because S-04 retention (FR + 12-month enforcement) must be able to delete aged quotes. "Immutable" here means content/status can never change, not that an approved row can never be removed; the forensic guarantee (FR-053) is that *as long as it exists* it is byte-for-byte unchanged.
- **Migration ordering.** Table + RLS enable must precede the policies; the RPC and trigger reference the table, so they come after. One timestamped migration file is fine, but order the statements: table → indexes → RLS enable → policies → trigger function + trigger → RPC + grant.
- **Local-only verification.** The SQL probe runs against local Supabase; it must not be wired into CI's build step (CI has no database). It is a manual/dev-gate artifact.

## Phase 1: Core schema & RLS

### Overview

Create the project's first migration: the `quotes` table, its constraints and indexes, and deny-by-default RLS with owner policies for the authenticated dentystka.

### Changes Required:

#### 1. First migration — table, constraints, indexes

**File**: `supabase/migrations/<YYYYMMDDHHmmss>_quotes_foundation.sql` (single migration; later phases append statements to this same file or sibling files — see note)

**Intent**: Define the `quotes` table as the sole domain table, with the columns S-01–S-04 need, so no follow-up migration touches this load-bearing table.

**Contract**: Table `public.quotes` with columns:
- `id uuid primary key default gen_random_uuid()`
- `patient_type text not null check (patient_type in ('child','adult'))`
- `status text not null default 'draft' check (status in ('draft','approved'))`
- `token text unique` (nullable until approval; populated by S-01)
- `patient_email text` (nullable; admin-only reference per FR-072)
- `content jsonb not null default '{}'::jsonb` (working tree; frozen on approval)
- `created_at timestamptz not null default now()`
- `approved_at timestamptz` (nullable; set on approval)

Indexes: unique index on `token` (partial `where token is not null` is acceptable), index on `created_at` for the admin list ordering (S-03) and retention scan (S-04).

#### 2. RLS enable + owner policies

**File**: same migration file

**Intent**: Turn RLS on and grant the single authenticated dentystka full CRUD on quotes, while denying the `anon` role any direct table access (its only path is the Phase 2 RPC).

**Contract**: `alter table public.quotes enable row level security;` plus granular per-operation policies for the `authenticated` role: `select`, `insert`, `update`, `delete`. Single-operator model — policies are `to authenticated using (true) with check (true)` (no per-user ownership column needed, as there is exactly one operator). **No policy** is created for `anon`, so anon is denied by default.

## Phase 2: Patient-read RPC & immutability trigger

### Overview

Add the two database objects that encode F-01's security guarantees: the public patient-read function and the approved-quote immutability trigger.

### Changes Required:

#### 1. `get_quote_by_token` RPC (SECURITY DEFINER)

**File**: same migration (statements after the table/RLS block)

**Intent**: Provide the single, anon-callable read path for the patient page that returns only patient-safe fields for a valid *approved* token and is indistinguishable from "not found" for any other input (FR-060), without exposing the table to `anon`.

**Contract**: `create function public.get_quote_by_token(p_token text) returns setof <whitelisted shape>` — returns at most one row of patient-safe columns (`id`, `patient_type`, `content`, `created_at`; **never** `patient_email`, `status`, `token`). Body filters `where token = p_token and status = 'approved'`. Declared `security definer`, `language sql` (or `plpgsql`) `stable`, with `set search_path = ''` and fully-qualified `public.quotes`. `revoke all on function ... from public;` then `grant execute ... to anon, authenticated;`.

```sql
-- security-critical shape; whitelist columns explicitly, pin search_path
create function public.get_quote_by_token(p_token text)
returns table (id uuid, patient_type text, content jsonb, created_at timestamptz)
language sql stable security definer set search_path = '' as $$
  select id, patient_type, content, created_at
  from public.quotes
  where token = p_token and status = 'approved'
$$;
```

#### 2. Approved-quote immutability trigger

**File**: same migration

**Intent**: Guarantee at the database that an already-approved quote can never be mutated (FR-053 forensic snapshot), regardless of any future app bug, while still permitting the one-time draft→approved transition.

**Contract**: A `plpgsql` trigger function raising an exception when `OLD.status = 'approved'`, attached as `before update on public.quotes for each row`. The draft→approved update (where `OLD.status = 'draft'`) passes through.

```sql
create function public.prevent_approved_update() returns trigger
language plpgsql as $$
begin
  if OLD.status = 'approved' then
    raise exception 'approved quotes are immutable (id=%)', OLD.id;
  end if;
  return NEW;
end;
$$;
create trigger quotes_immutable before update on public.quotes
  for each row execute function public.prevent_approved_update();
```

### Success Criteria:

#### Automated Verification:

- Migration still applies cleanly after these objects are added: `supabase db reset`
- `get_quote_by_token` is executable by `anon` and returns 0 rows for unknown/draft tokens, 1 patient-safe row for an approved token (asserted by Phase 4 probe)
- `UPDATE` on an approved row raises an exception; `UPDATE` on a draft row (incl. draft→approved) succeeds (asserted by Phase 4 probe)

#### Manual Verification:

- Confirmed `get_quote_by_token` returns no path to `patient_email`, `status`, or `token`.
- Confirmed the no-disclosure behavior (FR-060): unknown vs draft vs expired-later all look identical (empty result).

## Phase 3: Type & Zod contract

### Overview

Produce the TypeScript + Zod layer so the JSONB `content` contract and the row shape are both first-class types the rest of the app depends on.

### Changes Required:

#### 0. Declare `zod` as a direct dependency

**Command**: `npm install zod` (pin the major, e.g. `zod@^4`).

**Intent**: Phase 3.3 imports `zod` (`QuoteContentSchema`, `z.infer`) and CLAUDE.md mandates zod for validation, but `zod` is currently present only **transitively** (package-lock pins `^4.3.6`; it is not in `package.json` `dependencies`). Importing a transitive package directly is fragile — a future install/dedupe of the package that pulls it in can change or drop that version and silently break the type layer. Declare it explicitly before building the schemas. Note: target zod **v4** (its import surface differs from v3).

#### 1. Generated database row types

**File**: `src/db/database.types.ts`

**Intent**: Mechanically mirror the migrated schema so row types never drift from migrations.

**Contract**: Output of `supabase gen types typescript --local` (or `--project-id`), committed. Add a documented regen command to the change notes / README so future schema edits regenerate it. `content` will appear as `Json` here — Phase 3.3 gives it real structure.

#### 2. Domain entities & DTOs

**File**: `src/types.ts` (new)

**Intent**: Define the shared domain vocabulary every later slice imports — the names the whole app contracts on.

**Contract**: Export TypeScript types: `QuoteStatus` (`'draft' | 'approved'`), `PatientType` (`'child' | 'adult'`), `ToothStatus` (`'in-plan' | 'uncertain' | 'out-of-current-plan'`), `TreatmentType`, `Urgency`, `ToothEntry`, `Visit`, `GeneralItem`, `PricelistItemRef` (id + resolved name/price/range + `localAnesthesia` flag for snapshot), `QuoteContent` (the full `content` tree: teeth, visits, generalItems, optional resolved totals), `Quote` (row-level type composed from the generated row type with `content: QuoteContent`), and `PatientView` (the whitelisted shape the RPC returns). Re-export or alias the generated `Database` type for store code.

#### 3. Zod schemas for the JSONB contract

**File**: `src/types.ts` (alongside the types)

**Intent**: Give `content` a runtime validator so S-01/S-02 can validate form payloads and LLM output against the same single source of truth (FR-012).

**Contract**: Export `QuoteContentSchema` (Zod) whose inferred type equals `QuoteContent`, plus `ToothEntrySchema`, `VisitSchema`, `GeneralItemSchema`. Tooth dentition (milk/permanent) is **derived** from the tooth number (FR-022) — model it as a helper/derivation, not a stored field. Use `z.infer` to keep the TS types and Zod schemas from diverging.

**Validation posture (draft vs approval-ready)**: The DB default is `content = '{}'` and drafts are filled incrementally, so the schema must tolerate the empty/partial state. Model the top-level collections (`teeth`, `visits`, `generalItems`) with `.default([])` so `{}` and partially-filled drafts still parse, keeping a single source of truth. "Approval-ready" completeness (e.g. every `in-plan` tooth assigned to a visit, totals resolved) is **not** enforced here — that is an S-01 approval-time check layered on top, not a second schema.

### Success Criteria:

#### Automated Verification:

- `zod` is a declared dependency in `package.json` (not transitive): `grep '"zod"' package.json`
- Type checking passes: `npm run build` (runs `astro check`) or `npx astro check`
- Linting passes: `npm run lint`
- `z.infer<typeof QuoteContentSchema>` is assignable to `QuoteContent` (compile-time check / no `astro check` error)

#### Manual Verification:

- `QuoteContent` shape reviewed against FR-021–FR-032 (per-tooth fields, statuses, visits, general items) — every form field S-01 needs has a home.
- The `Json` vs `QuoteContent` boundary is clear: store code reads/writes `content` through the Zod schema, not the raw `Json` type.

#### 2. Contract-surfaces registry entry

**File**: `docs/reference/contract-surfaces.md` (new)

**Intent**: Record the load-bearing names this foundation introduces so downstream slices and reviews treat them as stable contracts.

Downstream slices (S-01/S-02) must honor it.

## Testing Strategy

### Unit Tests:

- No app-level unit tests in this slice (no app code beyond types). The Zod schema's correctness is covered by `astro check` (compile-time `z.infer` equivalence) and exercised for real in S-01.

### Integration Tests:

- The SQL probe (Phase 4) is the integration test for this slice: it drives RLS, the RPC, and the trigger against a real Postgres.

### Manual Testing Steps:

1. `supabase start` (Docker) then `supabase db reset` — migration applies with no errors.
2. Run the probe script — all assertion groups pass.
3. In `psql`, insert a draft quote as the authenticated role, then `select get_quote_by_token('<its token>')` while it is still draft → expect 0 rows.
4. Set it to `approved` (draft→approved succeeds), re-run the RPC → expect 1 patient-safe row, no `patient_email`.
5. Attempt any `update` on the approved row → expect an exception.

## Performance Considerations

Single-tenant, ~dozens of quotes/year (PRD `target_scale: small`). No performance budget. The `token` unique index and `created_at` index are the only access paths that matter; both are trivial at this scale.

## Migration Notes

This is the project's first migration — no existing data to migrate. `supabase db reset` is safe locally. Production apply happens via the normal Supabase migration flow during the first deploy that needs it (S-01); F-01 itself ships no runtime code, so it can land migrations-first without affecting the deployed Worker.
